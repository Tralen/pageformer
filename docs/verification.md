# Verification

The project verifies itself in layers: the Rust checks, Markdown lint, PDF/A conformance, the office package smoke tests, the HTML and EPUB structure, and the plain-text goldens. Every required tool installs at user level; `sudo` is only for optional system packages.

The versions below are the ones tested here. A newer tool is acceptable when the checks still pass.

## Tools

| Tool | Version | Purpose |
|---|---|---|
| `markdownlint-cli2` | 0.24.0 (markdownlint 0.42.0) | Markdown rules |
| `typst` | 0.15.1 | Standalone Typst compiler, matching the library version |
| `verapdf` | 1.30.3 | PDF/A conformance |
| `pdfinfo`, `pdffonts`, `pdftotext` | poppler-utils | PDF structure, fonts and text |

## Installation

Put the user binaries on `PATH` first:

```sh
export PATH="$HOME/.local/bin:$PATH"
```

Markdown lint. The `--prefix` keeps npm away from system directories:

```sh
npm install -g --prefix "$HOME/.local" markdownlint-cli2
```

Typst. The release is a `.tar.xz`; Python extracts it even when a local `xz` wrapper interferes with `tar -J`:

```sh
curl -L -o /tmp/typst.tar.xz https://github.com/typst/typst/releases/download/v0.15.1/typst-x86_64-unknown-linux-musl.tar.xz
mkdir -p /tmp/typst
python3 -m tarfile -e /tmp/typst.tar.xz /tmp/typst
install -m 755 /tmp/typst/typst-x86_64-unknown-linux-musl/typst "$HOME/.local/bin/typst"
```

veraPDF needs Java 11 or newer (`java -version`). The installer is interactive: choose `$HOME/.local/verapdf` and select the **veraPDF CLI** pack. The greenfield directory name carries the version, so use a glob:

```sh
curl -L -o /tmp/verapdf-installer.zip https://software.verapdf.org/releases/verapdf-installer.zip
unzip -q /tmp/verapdf-installer.zip -d /tmp
/tmp/verapdf-greenfield-*/verapdf-install -console
ln -sf "$HOME/.local/verapdf/verapdf" "$HOME/.local/bin/verapdf"
```

The optional structure tools come from the distribution:

```sh
sudo apt-get install qpdf poppler-utils mupdf-tools
```

Poppler provides `pdfinfo`, `pdffonts` and `pdftotext`; `qpdf --check` and `mutool info` add another structural opinion.

## Rust checks

Run these from the repository root:

```sh
cargo fmt --check
cargo clippy --workspace --all-targets --all-features -- -D warnings
cargo test --workspace --all-features -- --test-threads=1
cargo test --doc
cargo doc --no-deps
cargo build -p pageformer-publisher
cargo test -p pageformer-publisher
```

`cargo test --workspace --all-features` runs the engine, CLI and publisher tests. `--test-threads=1` keeps the Typst PDF test deterministic on a machine where several test binaries compete for resources. `cargo test --doc` runs the library doctests. `cargo doc --no-deps` documents the library; the publisher is a binary and has no separate documentation target. `cargo build -p pageformer-publisher` builds the window, and `cargo test -p pageformer-publisher` covers its pure state machine and path rules.

If a workspace run fails only on the Typst PDF determinism check while several binaries run, rerun the affected binary alone. The renderers are deterministic; the failure is in the test harness overlap, not in the generated bytes.

## Debian package

The packaging script is shell and is checked with `shellcheck`, then exercised end to end:

```sh
shellcheck packaging/build-deb.sh
packaging/build-deb.sh
lintian dist/pageformer_<version>_amd64.deb
dpkg-deb --info dist/pageformer_<version>_amd64.deb
dpkg-deb --contents dist/pageformer_<version>_amd64.deb
dpkg-deb -x dist/pageformer_<version>_amd64.deb /tmp/pageformer-deb
/tmp/pageformer-deb/usr/bin/pageformer --version
```

The script derives `SOURCE_DATE_EPOCH` from the last commit and remaps the Rust build paths, so two runs from the same checkout and toolchain produce the same SHA-256. `lintian` reports no errors; the four `embedded-library` errors are overridden with an explanation, because the libraries are pure Rust ports compiled into the binary and not system dependencies. The two `no-manual-page` warnings and the `no-changelog` error are fixed by the installed manual pages and the compressed change log.

The same build and checks run in `.github/workflows/deb.yml` when a release is published. The workflow also rewrites `SHA256SUMS` with the source archive and the package, attaches both with `--clobber`, and verifies the downloaded assets.

## Markdown lint

Use the repository configuration:

```sh
markdownlint-cli2
```

The configuration disables only rules that conflict with legal documents: line length, compact tables, explicit legal-numbering prefixes, multiple H1 section headings after a frontmatter title, and bold or italic lines used as headings. It ignores the session files and `target/`.

## PDF/A and structure

Validate the four committed examples:

```sh
verapdf --format text -f 2b assets/examples/publicacao/Contrato.pdf
verapdf --format text -f 2b assets/examples/publicacao/Embargos.pdf
verapdf --format text -f 2b assets/examples/technical/Report.pdf
verapdf --format text -f 2b assets/examples/brief/Brief.pdf
```

A passing run prints `PASS <path> 2b`. The test suite also asserts the PDF header, the PDF/A markers and byte-identical output across two renders; veraPDF checks the full profile. The technical report includes `Diagram.png` as a framed block image, so veraPDF also exercises the image and the page background. The brief adds an English letterhead, and `tests/brief.rs` covers its six outputs.

Poppler adds a quick structural and visual check:

```sh
pdfinfo assets/examples/publicacao/Contrato.pdf
pdffonts assets/examples/publicacao/Embargos.pdf
pdftotext assets/examples/publicacao/Contrato.pdf -
```

## ODT and DOCX packages

The tests unzip each package, parse every XML part with `roxmltree` and assert the structure, the styles and determinism. The LibreOffice smoke test confirms that the packages open without repair:

```sh
soffice --headless --convert-to pdf --outdir /tmp/odt-check assets/examples/publicacao/Contrato.odt assets/examples/publicacao/Embargos.odt assets/examples/technical/Report.odt assets/examples/brief/Brief.odt
soffice --headless --convert-to pdf --outdir /tmp/office-check assets/examples/publicacao/Contrato.docx assets/examples/publicacao/Embargos.docx assets/examples/technical/Report.docx assets/examples/brief/Brief.docx
```

The ODT examples match the PDF page counts (4, 4, 4 and 3). Editor rendering can still break a line differently, so the count is a regression guard, not a byte target. DOCX is a faithful package, not a page-count match: Word and LibreOffice lay out lines with their own engines.

## HTML documents

The tests render the four fixtures, check byte-identical output across two runs, parse the result and assert the semantic elements, the head metadata, the endnotes, the data-URI letterhead and the absence of a script or an unsafe link.

Regenerate the committed examples with:

```sh
cargo run -- --format html --confidential-file assets/examples/confidencial/embargos.ini --output assets/examples/publicacao assets/examples/escritorio/
cargo run -- --format html --output assets/examples/technical assets/examples/technical/Report.md
cargo run -- --format html --output assets/examples/brief assets/examples/brief/Brief.md
```

A direct file is written flat under `--output`, which is why the English commands write into the example directory. The file opens offline: the CSS is embedded, the images are data URIs and no network request is made. The `@page` letterhead and running content appear in print engines that implement those CSS Paged Media features; browsers that do not implement them omit the decoration without breaking the document.

The output is XHTML-compatible, so `xmllint` gives an independent well-formedness check:

```sh
xmllint --noout assets/examples/publicacao/Contrato.html assets/examples/publicacao/Embargos.html assets/examples/technical/Report.html assets/examples/brief/Brief.html
```

## EPUB packages

The tests unzip the package, assert that `mimetype` is first and stored, parse every XML part and check the container, manifest, spine, navigation, chapter split, relative image references, determinism and the absence of confidential values.

Regenerate the examples with:

```sh
cargo run -- --format epub --confidential-file assets/examples/confidencial/embargos.ini --output assets/examples/publicacao assets/examples/escritorio/
cargo run -- --format epub --output assets/examples/technical assets/examples/technical/Report.md
cargo run -- --format epub --output assets/examples/brief assets/examples/brief/Brief.md
```

`epubcheck` is the optional external validator. It is not installed in this environment; when it is available, run it against the four files:

```sh
epubcheck assets/examples/publicacao/Contrato.epub assets/examples/publicacao/Embargos.epub assets/examples/technical/Report.epub assets/examples/brief/Brief.epub
```

The package uses stored ZIP entries, a fixed timestamp and a deterministic identifier, so two runs must be byte-identical.

## Plain-text goldens

The text goldens in `assets/examples/publicacao/`, `assets/examples/technical/` and `assets/examples/brief/` are compared byte for byte by the tests. Regenerate them after a parser, model or text-renderer change and commit the result:

```sh
cargo run -- --format txt --confidential-file assets/examples/confidencial/embargos.ini --output assets/examples/publicacao assets/examples/escritorio/
cargo run -- --format txt assets/examples/technical/Report.md
cargo run -- --format txt assets/examples/brief/Brief.md
```

The `typst` command-line tool matches the library version used by the binary. The application compiles Typst in process, so the tool is a convenience for experimenting with generated source, not a runtime dependency.

## Publisher

`pageformer-publisher` is the minimal converter window in the `publisher/` workspace member. It calls `pipeline::render` and `pipeline::export` on a worker thread and never parses, resolves or writes by itself. Its unit tests cover the pure state machine, input acceptance, output paths and the source-root rule.

The window itself is the only manual part of the suite:

```sh
cargo run -p pageformer-publisher
```

Drop a Markdown file or click the drop box, choose a format, export and open the output. Confirm that a missing or invalid template produces a visible message instead of a crash, and that the window stays responsive while a render runs. With a `default_output` or a per-INI output configured, confirm that the window shows the resolved directory and its origin; choose a folder and confirm it overrides the automatic value; use Use default and confirm the automatic value returns. The unit tests cover the automatic resolution, the override, the origin label and the title contrast in both themes. The layout and behavior are described in [`pageweaver.md`](pageweaver.md), and the README shows the window.

## Confidential configuration

`tests/cli.rs` builds a temporary `XDG_CONFIG_HOME` with a public `config.yaml`, a `700` confidential directory, a `600` `confidential.yaml` and a mapped INI, then renders a document without `--confidential-file` and checks the resolved text. Another test proves that an explicit `--confidential-file` wins over the mapping. The same suite covers the output precedence: `--output` over the per-INI output, the per-INI output over `default_output`, `default_output` over the source folder, and an explicit confidential file that still uses `default_output`. It also proves that a per-INI output inside its source and a default output inside the source of a confidential document are rejected. The unit tests in `src/confidential/config.rs` cover the longest folder prefix, duplicate folders, invalid INI names, relative paths, unsupported versions, unknown keys, missing INIs, private permissions, the optional default output, unknown and duplicate output keys, and output paths inside their source.

The full configuration and failure rules are in [`confidential.md`](confidential.md).
